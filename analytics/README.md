# Analytics model for Metabase

## The constraint that decides the architecture

**Metabase cannot connect to Firestore.** Its bundled drivers are athena, bigquery,
clickhouse, databricks, druid, hive, mongo, oracle, presto, redshift, snowflake, sparksql,
sqlserver, starburst and vertica, plus Postgres and MySQL in core. There is no Firestore or
Firebase driver, and Metabase's own long-running request for one —
[metabase/metabase#4213](https://github.com/metabase/metabase/issues/4213) — was closed in
favour of routing through BigQuery instead.

So this is not a matter of pointing Metabase at what we have. Firestore stays the operational
store for the door tool, and the analytics layer is a separate relational copy.

```
Opera exports  ──▶  Firestore  ──▶  BigQuery  ──▶  Metabase
  (manual)          (the app)      (analytics)     (dashboards)
                         │              │
                    door tool      this schema
                    reads here     lives here
```

## Recommended: BigQuery

Not because it is the only option, but because it is the one with the least new machinery:

- **Firebase has a managed extension for exactly this**, *Stream Firestore to BigQuery*. Writes
  in Firestore land in BigQuery without us building or running a pipeline.
- Metabase has a first-class BigQuery driver.
- It is the path Metabase's own maintainers point at.
- At this volume — 841 reads and 204 writes across seven days, measured in the console — the
  cost is negligible.

**Postgres is a reasonable alternative** if you would rather not add BigQuery: the schema is
written to port with only the partitioning and array types changing, and the notes inline say
how. But then the Firestore-to-Postgres sync is ours to write and operate, which is real work
that the extension gives us for nothing.

### Two honest catches

**1. This needs the Blaze plan.** The BigQuery extension will not install on Spark. Your project
is on Starter Tier with the badge reading `spark`, and Firestore is under *AI SHARED QUOTA* —
so this is the same upgrade decision already on the table in `FIREBASE_SETUP.md`, not a new one.
It is worth knowing they are the same decision rather than two.

**2. The extension does not give you tables like these.** It gives you two objects per
collection — `<collection>_raw_changelog` and a `<collection>_raw_latest` view — with the
document body in a single JSON string column. That is a landing zone, not a model. Everything
in `schema.sql` sits *on top* of it, built by scheduled queries.

Anyone who has seen the extension's output and expected a star schema has been surprised by
this, so it is stated plainly here.

## What is in the model

`schema.sql` — five dimensions, four facts, four views.

| Fact | Grain | Additive? |
|---|---|---|
| `fact_room_night` | hotel × business_date × room | **No** — a periodic snapshot of who is in the house |
| `fact_meal_checkin` | hotel × business_date × room × meal_service | Yes — this is covers |
| `fact_package_forecast` | hotel × snapshot_date × stay_date × product | Yes within a snapshot |
| `fact_function_event` | hotel × business_date × venue × event | Yes |

`dim_rate_code` is the piece that carries the most weight: all 573 codes from Accor's Global
Rate Referential, generated by `scripts/generate-rate-referential.py` in the **same run** that
generates `src/lib/rateReferential.ts`. One command, two outputs, one workbook — so the app's
entitlement decisions and Metabase's rate dimension cannot drift apart. An app and a warehouse
quietly disagreeing about whether a rate includes breakfast is the kind of defect nobody
notices until a report is already wrong.

Load it with `analytics/seed_dim_rate_code.sql`, also generated.

## Three design decisions worth knowing before you query

### 1. No guest PII crosses this boundary

Firestore's `Guest` carries `guestName`, `accompanyingGuests`, `preferences`, `specialRequests`
and free-text notes the front office writes about named individuals. `CheckIn` carries
`checkedGuestNames` and `recordedBy`. **None of it is in this model, and that is deliberate.**

Metabase hands broad ad-hoc query access to everyone who can log in. A revenue manager asking
"how many covers on Tuesday" needs counts, never names — and every question this model exists
to answer is answerable from counts. Carrying the names would add real data-protection exposure
for no analytical return.

Staff names are excluded on the same reasoning: putting a server's name beside a productivity
count in a self-serve BI tool invites precisely the use it should not have. If per-shift
analysis is genuinely wanted later, that is a surrogate key into a separate,
access-controlled dimension — not a name column here.

`company_name` **is** kept. It is an organisation, not a person, and it is how you find out that
the Murata block is 68 rooms.

### 2. Breakfast entitlement is three-valued

`'included' | 'excluded' | 'unverified'` — never a boolean.

The app previously decided this by substring-matching a rate code and collapsing everything it
could not answer to "no". On one real export that silently refused breakfast to **60 adults who
were owed it**. A boolean column here would reintroduce that the moment somebody wrote
`COUNT(CASE WHEN entitled THEN 1 END)` and quietly lost the unknowns.

Three values force every query to say what it does with the third one. `vw_breakfast_reconciliation`
reports it as its own column because **the unverified count is not noise to be hidden — it is
the finding.** On 2 September:

| | confirmed | unverified | Opera forecast |
|---|---|---|---|
| Novotel | 20 pax | **93 pax** | 98 |
| ibis | 7 pax | **95 pax** | 43 |

### 3. Business date is not calendar date

The hotel day rolls at **04:00 Asia/Bangkok**. A check-in stamped 02:40 belongs to the previous
business date. Every fact is keyed on `business_date`, resolved upstream by
`src/lib/businessDate.ts`. Never re-derive it from a timestamp in SQL, and never use
`CURRENT_DATE()` as a business date — that is a bug this project has already had.

## The views, and why they exist

Rather than leaving people to reassemble these in the query builder and get the three-valued
entitlement wrong:

- **`vw_breakfast_reconciliation`** — what Opera forecast, what the rate codes entitle, and what
  was actually served, side by side per hotel per day. The number the business argues about.
- **`vw_unresolved_rate_codes`** — the work queue for whoever has Opera rate-code access, ranked
  by pax affected, with the block codes and companies attached. This is how `BGRE` at Novotel
  and `C01MRO` at ibis were identified as the two questions worth asking first.
- **`vw_breakfast_attendance`** — no-shows and attendance rate, computed **only over confirmed
  entitlement**. An attendance rate over unverified rooms is not a rate; it is an artefact of
  how many codes nobody has looked up yet.
- **`vw_function_space_day`** — the meeting-room day sheet, and the one place `revenue_thb`
  belongs.

## What is not decided

**Scope.** This models the F&B and function-space domain — the app I have verified data for.
If Metabase is meant to replace the wider reporting practice too (the weekly owner reports, the
RevMax packets, the GRC subtotals), that is a materially larger model: it needs room-revenue,
ADR, RevPAR, segment and budget-versus-actual facts, and its sources are the OTB and GRC
workbooks rather than the Opera exports. Say the word and I will extend it; I have not assumed
it.

**Nothing here is deployed.** This is the schema and the seed. Loading it needs the Blaze
upgrade, and the transform from the extension's JSON landing tables into these facts is the
next piece of work.
